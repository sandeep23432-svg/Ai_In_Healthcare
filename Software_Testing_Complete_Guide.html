Module 1: Software Testing Basics & Principles
🧠 Software Testing Kya Hai?
Bhai, Software Testing ek aisa process hai jisme hum software ko check karte hain ki woh sahi se kaam kar raha hai ya nahi. Jaise ek teacher exam paper check karta hai, usi tarah tester software check karta hai.
Software Testing is the process of evaluating a software application or system to identify defects and ensure that it meets the specified requirements. It involves executing the software under controlled conditions to detect errors, gaps, or missing functionalities.
Software Testing is the process of evaluating and verifying that a software product or application does what it is supposed to do. It involves executing a program or application with the intent of finding software bugs (errors or other defects). Goals include: Quality Assurance and Defect Identification.

🎯 Goals of Software Testing (3 Categories)

1. Immediate Goals

Turant jo karna hai — yani bugs dhundhna. Jitna jaldi bug milega, utna achha!

Bug Discovery: Finding errors as early as possible in the SDLC.

2. Long-term Goals

Long run mein product ki quality acchi honi chahiye — reliability, quality, customer satisfaction.
  • Quality: Testing ensures the software is correct, efficient, and reliable.
  • Reliability: Measure of confidence that software will not fail.
  • Customer Satisfaction: Complete testing leads to satisfaction.
  • Risk Management: Testing helps eliminate or minimize risks.

3. Post-implementation Goals

Product release ke baad ke goals:
  • Bug Prevention: Past test history helps prevent future bugs.
  • Reduced Maintenance Cost: Fewer bugs = less maintenance cost.
  • Improved Testing Process: Each project improves future testing.

🔴 7 Principles of Software Testing
Yeh 7 principles sabse important hain Module 1 mein. Ek ek yaad karo!
1
Testing Shows Presence of Defects, Never Absence
Testing se hum prove kar sakte hain ki bug HAI, lekin yeh nahi prove kar sakte ki bug NAHI hai.
Testing can only show that defects are present. It cannot prove the software is 100% defect-free, even if all test cases pass. Example: 50 test cases pass on login page, but a special character input still crashes the system later.
2
Exhaustive Testing is Impossible
Har possible input test karna impossible hai. Socho login mein kitne password combinations ho sakte hain!
Testing all possible inputs, paths, and combinations is practically impossible due to infinite input combinations, multiple environments, and time/cost constraints. Instead, techniques like Equivalence Partitioning and BVA are used.
3
Early Testing
Jitna jaldi testing shuru karo, utna sasta padega. Requirements mein bug milna, code mein milne se 100x sasta hai!
Testing activities should start as early as possible in the SDLC. The cost of fixing a defect increases exponentially as the project progresses. Early testing saves time and money.
4
Defect Clustering (80/20 Rule)
80% bugs sirf 20% modules mein hote hain. Toh testing ka focus un modules pe karo!
A small number of modules contain most of the defects. This follows the Pareto Principle (80/20 rule): ~80% of defects are found in 20% of modules. These are usually complex or frequently modified modules.
5
Pesticide Paradox
Ek hi test baar baar chalao toh naye bugs nahi milenge — jaise ek hi pesticide se insects immune ho jaate hain!
If the same set of tests are repeated, they will no longer find new bugs. Test cases must be regularly reviewed and updated with new test cases to find more defects.
6
Testing is Context Dependent
Banking app aur gaming app same tarike se test nahi hote!
Testing is done differently depending on the context. Safety-critical software (medical, aviation) is tested differently than a gaming app. Different domains require different testing approaches.
7
Absence of Errors Fallacy
Software bug-free ho, lekin user ki zaroorat hi na poori ho — toh kya fayda? 0 bugs but useless software!
A software can be 99% bug-free but still fail if it doesn't meet user requirements or solve the intended problem. Building the right product is equally important as building it correctly.

Module 2: Verification, Validation & Coverage
🔍 Verification Techniques
Verification mein code RUN nahi karte — sirf documents check karte hain (static testing).

1. Code Review

A systematic examination of source code by peers or tools to find bugs, improve code quality, and ensure coding standards.

2. Walkthrough

Author apna code/design 2-7 logon ko step by step samjhata hai. Koi formal rules nahi hote.
In a walkthrough, the author of the software document presents the document to 2-7 participants. Participants are NOT expected to prepare in advance. The author introduces the content and all participants can ask questions freely. Goal: informal defect detection.

3. Inspection

Walkthrough se zyada formal! 3-6 log + ek moderator. Checklist use hoti hai. Formal report banti hai.
Inspection is the most structured and formal verification method. A team of 3-6 participants led by an impartial moderator uses checklists to detect defects. After meeting, a formal report is prepared. It is more effective than walkthroughs.

4. Static Analysis Tools

Automated tools that analyze code without executing it. They check coding standards, detect memory leaks, security vulnerabilities, etc. Examples: SonarQube, PMD, FindBugs.

📊 Coverage Techniques — NUMERICALS IMPORTANT!

1. Statement Coverage

Har statement (line of code) kam se kam ek baar execute honi chahiye.
Statement Coverage = (Statements Executed / Total Statements) × 100

2. Decision/Branch Coverage

Har if/else ka dono branch (true aur false) test hona chahiye.
Decision Coverage = (Decision Outcomes Tested / Total Decision Outcomes) × 100

3. Path Coverage

Start se end tak ke saare possible paths test hone chahiye. Yeh sabse exhaustive hai!
Path Coverage = (Paths Executed / Total Possible Paths) × 100
Coverage TypeWhat it EnsuresTest Cases Needed
StatementEach statement runs at least onceFewest
DecisionEach True/False branch is testedMore than statement
PathEvery unique path from start to end is testedMost (exhaustive)
🔢 Coverage Numericals — Practice Set
📘 Numerical 1: Statement Coverage

Given code has 10 total statements. Test cases execute 8 statements.

Formula: Statement Coverage = (Executed / Total) × 100
Step 1: Executed statements = 8
Step 2: Total statements = 10
Calculation: (8 / 10) × 100 = 80%
✅ Statement Coverage = 80%
📘 Numerical 2: Decision Coverage

Code has 3 if-else conditions (so 6 total decision outcomes = 3×2). Tests cover 4 outcomes.

Formula: Decision Coverage = (Outcomes Tested / Total Outcomes) × 100
Step 1: Total decision outcomes = 3 decisions × 2 (True/False) = 6
Step 2: Tested outcomes = 4
Calculation: (4/6) × 100 = 66.67%
✅ Decision Coverage = 66.67%
📘 Numerical 3: Path Coverage (from PPT code example)

Code: if A > 10: → if B > 5: print("P1") else: print("P2") else: → if B > 0: print("P3") else: print("P4")

Step 1: How many independent decisions? Decision 1: A>10 (T/F), Decision 2: B>5 (T/F), Decision 3: B>0 (T/F)
Step 2: Possible Paths = 4 (P1: A>10 T & B>5 T, P2: A>10 T & B>5 F, P3: A>10 F & B>0 T, P4: A>10 F & B>0 F)
Step 3: Test Cases needed = 4 (one per path)
Test Data: P1: A=15, B=6 | P2: A=15, B=3 | P3: A=5, B=2 | P4: A=5, B=-1
✅ 4 test cases required for 100% path coverage
📘 Numerical 4: All Coverage Types Comparison

Code: if (x>0) { if (y>0) { print("A"); } else { print("B"); } } else { print("C"); }

Statements: 5 total (if x>0, if y>0, print A, print B, print C)
Statement Coverage: Need only 1 test case to hit any path → e.g., x=5, y=5 covers 3 statements. Need 2 cases for all 5 → x=5,y=-1 (covers B) and x=-1 (covers C)
Decision Coverage: Need x>0 True&False, y>0 True&False → Min 3 test cases
Path Coverage: Path1: x>0,y>0→A | Path2: x>0,y≤0→B | Path3: x≤0→C → 3 paths, 3 test cases
✅ Statement: 2 TCs | Decision: 3 TCs | Path: 3 TCs
🏗️ Types of Verification (SRS, SDD, Program)

1. SRS Verification

Goal: Ensure the Software Requirements Specification is correct, complete, consistent, and unambiguous. Activities: checking if requirements are clear and testable, no contradictions exist, all stakeholder needs are captured. Example: In an online banking app, verifying "The system must allow money transfer" is properly specified with limits, constraints, and error cases.

2. SDD Verification

Goal: Ensure design matches requirements and is feasible to implement. Activities: reviewing architectural diagrams, Data Flow Diagrams, Database Schema, module interactions. Example: Checking that the "Transfer Money" module design includes balance check and maps to SRS requirements.

3. Program/Code Verification

Goal: Ensure code correctly implements the design. Activities: code reviews, walkthroughs, static analysis, checking coding standards and logic. Example: Reviewing the transferMoney() function to confirm it follows design (balance check, transaction log, rollback if failed).
✅ Software Quality & Reliability
Software Quality: The degree to which a software product meets its specified and implied needs. Quality isn't just about a lack of bugs; it's about building a product that is "fit for purpose."
Software Reliability: The probability that a software system will perform its required functions without failure for a specified time in a specified environment.
Quality vs Reliability analogy: Ek car high-quality materials se bani ho (quality), lekin agar baar baar band ho jaaye toh woh reliable nahi hai!
Module 3: Types of Testing
🔬 Unit Testing
Lego analogy: Puri castle banana se pehle, ek ek Lego piece check karo ki sahi fit ho rahi hai ya nahi. Usi tarah, ek ek function test karo!
Unit Testing is a level of software testing where individual components or functions are tested in isolation to ensure they perform as expected. Usually performed by developers using frameworks like JUnit (Java) or pytest (Python).
Example: Testing a function `calculate_discount(price, coupon)` to ensure it applies the correct discount before integrating into the checkout system.
Key Point: "In Isolation" — baaki koi component nahi hota. Stubs/Mocks use hote hain.
🔗 Integration Testing
Sab Lego pieces alag alag sahi hain — ab inko attach karo. Ek perfect piece doosre se sahi fit ho raha hai ya nahi, yeh check karte hain!
Integration Testing verifies that different modules or components of the software work together as intended when integrated. It checks the interfaces and interaction between modules.
Real-world Analogy: In a restaurant, chef, waiter, and cashier all work fine individually. But if the waiter forgets to tell the chef your order, the customer remains hungry — that's an integration bug.

Software Example: Testing if the Login module correctly passes user credentials to the Dashboard and retrieves correct user data.
👥 User Acceptance Testing (UAT)
Car bana li — ab customer ko test drive dedo! UAT ensure karta hai ki product real user ki problem solve karta hai.
UAT is the final phase of testing performed by clients or end users to confirm that the system meets business requirements and is ready for production deployment.
Real-world Analogy: A restaurant invites guests for a soft opening before the grand launch to check if dishes meet expectations.

Software Example: Bank staff test the new loan application workflow to confirm it matches their business process.
🔬 Alpha vs Beta Testing
Alpha = Ghar ke andar khud test karo. Beta = Kuch selected users ko dedo test karne ke liye!

Real-world: A game developer plays their game internally (Alpha), then releases a demo to selected players (Beta) for real feedback.
💨 Smoke Testing vs Sanity Testing
Bahut confusing hain yeh dono! Yaad rakho:
🚬 Smoke = Naya build aaya → pehle check karo ki zinda hai ya nahi
🧠 Sanity = Bug fix hua → sirf woh part check karo
Smoke Testing: Preliminary test that checks the stability of the software build. Ensures critical features work before detailed testing begins. Like turning on a machine — if no smoke, it's safe to proceed.
Sanity Testing: Focused testing after minor code fixes or patches to verify that specific changes work and related features remain unaffected. Like fixing a car's headlight — check only the lights, not the entire car.
AspectSmoke TestingSanity Testing
When doneAfter new build/deploymentAfter minor bug fix or patch
ScopeBroad — critical featuresNarrow — specific changed area
PurposeIs the build stable for testing?Is the specific fix correct?
Also calledBuild Verification TestingSubset Regression Testing
🔁 Regression Testing
TV mein ek loose wire fix kiya → ab check karo ki volume, color, brightness sab theek hai! Ek change se baaki cheezein toot jaati hain, woh check karna = Regression Testing.
Regression Testing ensures that new changes, updates, or bug fixes have not broken existing functionalities in the system.
Regression Testing is performed after every code change or bug fix to verify that previously working features still work correctly. It uses automation tools like Selenium for efficiency. Example: After adding a coupon feature, re-test cart, checkout, payment, and order history.
Regression Testing is the MOST commonly automated test type — it's repeated every sprint/build!

🐒 Monkey Testing
Apna phone ek monkey ko de do — woh random button press karega. Agar app crash na ho, toh robust hai! Usi tarah random inputs deke system test karna = Monkey Testing.
Monkey Testing is a random testing technique where testers input random data and perform random actions to check system stability and crash behavior. Purpose: to test robustness against unpredictable user behavior.
Example: E-commerce App — tester enters random characters in name/address fields, clicks 'Buy Now' repeatedly, navigates rapidly between pages. If app crashes, it reveals weak input handling or memory management.
🔄 Re-Testing
Leaky tap fix kiya → ab wahi tap check karo ki leak band hua ya nahi. Sirf failed test case dobara run karna = Re-Testing.
Re-Testing is performed after fixing a defect to verify that the issue has been resolved. It focuses ONLY on failed test cases from previous cycles.
Difference from Regression: Re-testing is targeted (only failed TCs), while Regression testing is broad (all existing TCs). Example: After resolving a login bug, QA executes only the failed test case 'Invalid password handling'.

🎯 Ad Hoc Testing & Sub-Types
Ad Hoc Testing: Unstructured, informal testing performed without test cases. Relies on intuition, domain knowledge, and creativity. Goal: detect defects quickly outside formal test conditions.

1. Pair Testing

Two testers work together on the same machine — one operates (tester) and one observes (reviewer). They switch roles periodically. Promotes knowledge sharing and better defect detection. Like pair programming but for testing.

2. Exploratory Testing

Simultaneous learning, test design, and test execution. Tester explores the application without predefined test cases, designs tests based on what they discover. Best when: requirements are unclear or rapidly changing. Example: Tester begins testing a new feature, discovers defects, and simultaneously designs new test cases based on system behavior.

3. Iterative Testing

Testing is performed in cycles/iterations, continuously testing newly added features. Each iteration improves test strategy based on feedback from earlier cycles. Used in Agile development. Example: During sprint development, testers continuously test new features and update strategies based on feedback.

4. Defect Seeding

Intentionally inserting known defects into the system to measure testing effectiveness and test coverage quality. Used in safety-critical industries (aviation, healthcare).
Teacher ne assignment mein deliberately galti daali → dekha koi pakad pata hai ya nahi! Usi tarah testers jaan ke bugs daalte hain software mein.
🔢 Defect Seeding Numericals — VERY IMPORTANT!
Test Case Effectiveness = (Seeded Defects Found / Total Seeded Defects) × 100
Actual Defects Found = (Effectiveness% / 100) × Total Actual Defects
Total Defects = (Defects Found / Effectiveness)

Given: Seeded = 10, Found = 6
Part 1 - Effectiveness: (6/10) × 100 = 60%
Part 2 - If 40 actual defects: 60% × 40 = 24 defects found
Part 3 - If 30 defects found: Total = 30 / 0.60 = 50 actual defects
✅ Effectiveness=60% | Found=24 | Total=50
📘 Numerical 2: 20 seeded, 14 found. If 70 actual defects exist, how many found?
Step 1 - Effectiveness: (14/20) × 100 = 70%
Step 2 - Actual defects found: 70% × 70 = 49 defects
✅ Effectiveness=70% | Actual defects found=49
📘 Numerical 3: 25 seeded defects, 20 found. Team claims 35 defects found in total. How many actual defects were in system?
Step 1 - Effectiveness: (20/25) × 100 = 80%
Step 2 - Actual defects found (non-seeded): 35 - 20 = 15 actual defects found

Testing Techniques: White Box & Black Box
⬜ White Box Testing
Glass/Clear Box Testing bhi kehte hain. Tester ko code pata hota hai — andar ka structure dekhke test karte hain. Developer level ka knowledge chahiye!
White Box Testing (also called Glass Box, Clear Box, or Structural Testing) focuses on the internal logic, structure, and code implementation of the software. Performed by developers or test engineers with programming knowledge.

Techniques:

  • Statement Coverage
  • Branch/Decision Coverage
  • Condition Coverage
  • Path Coverage
  • Loop Testing

Loop Testing:

Tests loops for: Zero iterations, One iteration, Typical iteration, Maximum iteration, One more than maximum (for failure boundary).
⬛ Black Box Testing
Code nahi pata, sirf requirements pata hain. Tester ek black box dekh raha hai — andar nahi jaanta. User ki tarah test karta hai!
Black Box Testing focuses on the system's behavior from an external perspective, without knowledge of internal code. Testers verify that outputs are correct for given inputs based on requirements/specifications.

Techniques:

  • Equivalence Partitioning
  • Boundary Value Analysis (BVA)
  • Decision Table Testing
  • State Transition Testing
  • Use Case Testing

🔢 Equivalence Partitioning & BVA Numericals

Equivalence Partitioning (EP)

Inputs ko groups mein baanto — ek group ka ek representative test karo. Example: 18-60 age valid hai. Toh 3 partitions: <18, 18-60, >60.
📘 Numerical 1: Age input 18-60 (from PPT)
Valid Partition: 18 to 60
Invalid Partition 1: Less than 18
Invalid Partition 2: Greater than 60
Test Cases: 17 (invalid) | 30 (valid) | 65 (invalid)
✅ 3 Equivalence Classes → 3 Test Cases (minimum)

Boundary Value Analysis (BVA)

Boundaries ke aas paas test karo — yahan bugs zyada milte hain! ≤, ≥ conditions mein off-by-one errors hote hain.
BVA mein: minimum-1, minimum, minimum+1, maximum-1, maximum, maximum+1 — yahi 6 values test karo!
📘 Numerical 2: Marks 0-100 BVA (from PPT)
Range: Valid = 0 to 100
BVA Values: -1, 0, 1, 99, 100, 101
-1: Invalid (below minimum)
0: Valid (minimum boundary)
1: Valid (minimum+1)
99: Valid (maximum-1)
100: Valid (maximum boundary)
101: Invalid (above maximum)
✅ Total 6 Test Cases for BVA

7 chars: Invalid | 8 chars: Valid (min boundary)
9 chars: Valid | 15 chars: Valid

🔄 State Transition Testing
System ke different states (conditions) mein kaise behave karta hai — yeh check karna = State Transition Testing.
Example: Login System
State 1 (Logged Out) → [Enter valid credentials] → State 2 (Logged In)
State 2 (Logged In) → [Click Logout] → State 1 (Logged Out)
State 1 → [3 wrong attempts] → State 3 (Account Locked)
State 3 → [Admin unlock] → State 1 (Logged Out)
Test Metrics: Formulas & Numericals
📐 All Important Formulas
Test Case Effectiveness = (Defects Detected / Test Cases Run) × 100
Passed TC% = (Tests Passed / Tests Executed) × 100
Failed TC% = (Tests Failed / Tests Executed) × 100
Blocked TC% = (Tests Blocked / Tests Executed) × 100
Fixed Defects% = (Defects Fixed / Defects Reported) × 100
Accepted Defects% = (Defects Accepted / Total Defects Reported) × 100
Deferred Defects% = (Defects Deferred / Total Defects Reported) × 100
Rework Effort Ratio = (Rework Effort / Total Effort) × 100
Defect Density = Number of Defects / Size (KLOC or Function Points)

STLC: Software Testing Life Cycle
🔄 STLC Overview
STLC ek structured process hai jisme software testing ke saare phases hote hain. Jaise SDLC mein development ke phases hote hain, usi tarah STLC mein testing ke phases!
STLC (Software Testing Life Cycle) defines a sequence of activities performed during testing to ensure software quality. Each phase has specific entry criteria, activities, deliverables, and exit criteria.
📋 7 Phases of STLC — Detail Mein
1
Requirement Analysis
SRS padhke samjho — kya test karna hai!
Objective: Understand what needs to be tested. Activities: Analyze SRS, identify testable items, review with QA team. Deliverables: RTM (Requirement Traceability Matrix), Requirement Review Report. Entry: Approved SRS. Exit: Requirement understanding confirmed.
2
Test Planning
Strategy banao — kya test karenge, kab, kaise, kaun karega!
Objective: Define testing strategy, scope, and objectives. Activities: Identify testing objectives, schedule, resources, tools, levels. Deliverables: Test Plan document, Effort Estimation. Entry: Requirement documents ready. Exit: Approved Test Plan.
3
Test Case Design
Actual test cases likhte hain — positive + negative, functional + non-functional!
Objective: Create detailed test cases and prepare test data. Activities: Write test cases for all scenarios, review test scripts. Deliverables: Test Case Document, Test Data. Entry: Approved Test Plan. Exit: Reviewed test cases and data.
4
Test Environment Setup
Server configure karo, database setup karo, tools install karo — phir smoke test se verify karo!
Objective: Prepare environment for testing. Activities: Configure servers, databases, tools; perform smoke testing. Deliverables: Environment setup confirmation, smoke test results. Entry: Approved Test Plan and Test Cases. Exit: Environment ready.
5
Test Execution
Ab actually test cases run karo aur results record karo!
Objective: Execute test cases and record results. Activities: Run test cases, compare actual vs expected results, log defects. Deliverables: Test Execution Report, Defect Reports. Entry: Environment ready, test data prepared. Exit: All cases executed.
6
Defect Reporting & Tracking
Bug milne pe report likho, developer ko dedo fix karne ke liye, phir verify karo!
Objective: Identify, report, and track defects to closure. Activities: Log defects, assign severity/priority, verify fixes, regression testing. Deliverables: Updated Defect Log. Entry: Defects found during testing. Exit: All critical defects resolved.
7
Test Closure
Testing khatam! Summary report banao, lessons seekho, sign-off lo!
Objective: Summarize and evaluate the testing process. Activities: Analyze test coverage, defect metrics, document lessons learned. Deliverables: Test Summary Report (TSR), Lessons Learned Document. Entry: All test cycles completed. Exit: Deliverables signed off.
📋 RTM — Requirement Traceability Matrix
RTM ek table hai jo requirements ko test cases se link karta hai. Isse ensure hota hai ki har requirement ke liye test case hai!
Requirement Traceability Matrix (RTM) is a document that maps and traces user requirements with test cases. It ensures complete test coverage — every requirement has at least one test case, and every test case traces back to a requirement.

📝 What is a Test Case?
A Test Case is a set of conditions or steps to verify that a software feature works as expected. It specifies inputs, execution conditions, testing procedure, and expected results.

Components of a Test Case:

  1. Test Case ID — Unique identifier (e.g., TC_EC_01)
  2. Test Description — What is being tested
  3. Preconditions — Setup needed before test
  4. Test Steps — Step-by-step actions
  5. Test Data — Input values used
  6. Expected Result — What should happen
  7. Actual Result — What actually happened
  8. Status — Pass/Fail

📌 2-Mark Questions (Short Answer)

Q1. Define Software Testing. 2 Marks
Software Testing is the process of evaluating and verifying that a software product does what it is supposed to do. It involves executing a program to find software bugs, errors, or missing requirements. The two main goals are: (1) Quality Assurance and (2) Defect Identification.
Q2. What is the difference between Verification and Validation? 2 Marks
Verification ensures the product is built correctly as per design specifications. It is process-oriented and uses activities like reviews, inspections, walkthroughs. It answers: "Are we building the product right?"

Validation ensures the right product is built that meets user needs. It is product-oriented and uses activities like functional testing, UAT. It answers: "Are we building the right product?"
Q3. What is the Pesticide Paradox? 2 Marks
The Pesticide Paradox is the 5th principle of software testing. It states that if the same set of test cases are repeated over and over, they will no longer find new bugs — just like how pests become immune to the same pesticide used repeatedly. Therefore, test cases must be regularly reviewed, revised, and new test cases must be written to explore different parts of the software.
Q4. Differentiate between Smoke Testing and Sanity Testing. 2 Marks
Smoke Testing: Performed after a new build to check if the build is stable enough for further testing. It is broad in scope — testing critical core features. Also called Build Verification Testing.

Sanity Testing: Performed after minor bug fixes or patches to verify that the specific change works correctly without affecting other features. It is narrow in scope — focused on the changed area only.
Q5. What is Defect Seeding? Give its formula. 2 Marks
Defect Seeding is a technique where known defects are intentionally inserted into a system to measure testing effectiveness. It is used in safety-critical industries like aviation and healthcare.

Formula: Test Case Effectiveness = (Number of Seeded Defects Found / Total Seeded Defects) × 100

Example: If 10 defects are seeded and 6 are found, Effectiveness = (6/10) × 100 = 60%.
Q6. State the principle "Defect Clustering." 2 Marks
Defect Clustering is the 4th principle of software testing. It states that a small number of modules contain most of the defects in the software. This follows the Pareto Principle (80/20 rule): approximately 80% of defects are found in 20% of the modules. These defect-prone modules are usually complex, newly developed, or frequently modified. Testers focus more effort on these modules to optimize resources and improve quality.
Q7. What is Re-Testing? How is it different from Regression Testing? 2 Marks
Re-Testing: Performed after a defect is fixed, to verify that the specific issue has been resolved. It focuses only on previously failed test cases.

Regression Testing: Performed after any code change to ensure that new changes haven't broken existing functionalities. It covers all test cases, not just failed ones.

Key difference: Re-testing is narrow (only failed TCs), Regression is broad (all TCs).
Q8. Define Boundary Value Analysis with example. 2 Marks
Boundary Value Analysis (BVA) is a Black Box testing technique that focuses on testing at the boundaries of input ranges, where bugs are most likely to occur.

Example: If marks should be between 0 and 100, the BVA test cases are: -1 (invalid), 0 (min boundary), 1 (min+1), 99 (max-1), 100 (max boundary), 101 (invalid). Total: 6 test cases.

📌 6-Mark Questions

Q1. Explain the 7 Principles of Software Testing with examples. 6 Marks
The 7 principles of software testing are:

  1. Testing shows presence of defects, not absence: Testing can only prove bugs exist, never that software is bug-free. Even after all 50 test cases pass, a special character in username may crash the login system.
  2. Exhaustive testing is impossible: Testing all possible inputs is impractical. Techniques like Equivalence Partitioning and BVA are used instead to select representative test cases.
  3. Early testing: Testing should start as early as SDLC allows. A defect found in requirements phase costs 100x less to fix than one found in production.
  4. Defect clustering (80/20 rule): ~80% of defects exist in ~20% of modules. Testing efforts should be focused on these high-risk modules.
  5. Pesticide Paradox: Running the same tests repeatedly won't find new bugs. Test cases must be regularly updated and new ones added.
  6. Testing is context dependent: A banking app requires security-focused testing; a gaming app requires performance testing. No single approach fits all.
  7. Absence of errors fallacy: Even a bug-free system is useless if it doesn't meet user requirements. Both correctness and usefulness matter.
Q2. Explain the phases of STLC with entry/exit criteria and deliverables. 6 Marks
STLC (Software Testing Life Cycle) is a sequence of specific activities performed during testing to ensure software quality. It has 7 phases:

  1. Requirement Analysis: Objective: understand what needs testing. Deliverables: RTM, Requirement Review Report. Entry: Approved SRS. Exit: Requirements understood.
  2. Test Planning: Objective: define strategy, scope, resources. Deliverables: Test Plan, Effort Estimation. Entry: Requirements ready. Exit: Approved Test Plan.
  3. Test Case Design: Objective: create detailed test cases. Deliverables: Test Case Document, Test Data. Entry: Approved Test Plan. Exit: Reviewed test cases.
  4. Test Environment Setup: Objective: configure testing environment. Deliverables: Environment confirmation, smoke test results. Entry: Approved TCs. Exit: Environment ready.
  5. Test Execution: Objective: run tests, record results. Deliverables: Test Execution Report, Defect Reports. Entry: Environment ready. Exit: All TCs executed.
  6. Defect Reporting & Tracking: Objective: log and track defects. Deliverables: Defect Log. Entry: Defects found. Exit: Critical defects resolved.
  7. Test Closure: Objective: summarize testing. Deliverables: Test Summary Report (TSR), Lessons Learned. Entry: All cycles complete. Exit: Signed-off deliverables.
Q3. Explain Equivalence Partitioning and Boundary Value Analysis with numerical examples. 6 Marks
Equivalence Partitioning (EP):
A Black Box testing technique that divides input data into partitions where all values in a partition are expected to behave the same. One value from each partition is tested.

Numerical Example: Age field valid range: 18 to 60
• Partition 1 (Invalid): Age < 18 → Test with 17
• Partition 2 (Valid): Age 18-60 → Test with 30
• Partition 3 (Invalid): Age > 60 → Test with 65
Total test cases: 3

Boundary Value Analysis (BVA):
Tests at the exact boundaries of valid ranges, where bugs are most likely. For range [min, max], test: min-1, min, min+1, max-1, max, max+1.

Numerical Example: Marks field valid range: 0 to 100
Test values: -1 (invalid), 0 (valid-min), 1 (valid), 99 (valid), 100 (valid-max), 101 (invalid)
Total BVA test cases: 6

Key Difference: EP reduces test cases by grouping. BVA focuses specifically on boundary values where off-by-one errors occur.

📌 8-Mark Questions

Q1. Explain White Box and Black Box Testing. Compare them and give examples of techniques used in each. 8 Marks
WHITE BOX TESTING:
Also known as Glass Box, Clear Box, or Structural Testing. The tester has full knowledge of the internal code structure and logic.
Performed by: Developers or test engineers with programming knowledge.
Focus: Internal code paths, logic, loops, conditions.

Techniques:
1. Statement Coverage: Every statement executes at least once. Formula: (Statements Executed/Total Statements)×100
2. Decision/Branch Coverage: Every True/False branch of every decision is tested.
3. Path Coverage: Every possible execution path from start to end is tested. Most exhaustive.
4. Loop Testing: Tests zero, one, typical, and maximum iterations.

Example: Testing payment gateway code — ensuring all encryption API calls are triggered, exception handling works, and retry loops terminate correctly.

Benefits: Early defect detection, optimized code coverage, detects logical errors.
Limitations: Time-consuming, requires coding expertise.


BLACK BOX TESTING:
Also known as Behavioral or Specification-Based Testing. The tester has no knowledge of internal code; testing is based on requirements only.
Performed by: QA testers (no coding knowledge required).
Focus: System behavior, functionality, outputs.

Techniques:
1. Equivalence Partitioning: Divide inputs into classes; test one from each.
2. Boundary Value Analysis: Test at boundaries (min-1, min, min+1, max-1, max, max+1).
3. Decision Table Testing: Map all condition combinations to actions.
4. State Transition Testing: Test system behavior when transitioning between states.

Example: Testing Amazon checkout — verifying users can add/remove items, discounts apply, payment errors show user-friendly messages.

Q3. Explain different types of testing: Unit, Integration, UAT, Smoke, Sanity, Regression. 8 Marks
1. UNIT TESTING:
Individual components or functions are tested in isolation. Done by developers using JUnit (Java) or pytest (Python). Example: Testing calculate_discount(price, coupon) before integrating into checkout.

2. INTEGRATION TESTING:
Tests that different modules work together correctly. Checks interfaces and data flow between components. Analogy: In a restaurant, chef, waiter, cashier work fine individually, but if the waiter forgets to tell the chef the order, the customer goes hungry — that's an integration bug.

3. USER ACCEPTANCE TESTING (UAT):
Final testing phase done by actual end-users to verify the system meets business requirements. Done before production deployment. Example: Bank staff testing a new loan application workflow.

4. SMOKE TESTING:
Preliminary test to check if a new build is stable enough for detailed testing. Tests critical core functionalities only. Done immediately after a new build. Example: After deployment, verify login, product search, and checkout work before full testing.

5. SANITY TESTING:
Focused testing after a minor bug fix or patch to verify the fix works and related areas are unaffected. Example: After fixing a coupon bug, test only the discount calculation and checkout process.

6. REGRESSION TESTING:
Ensures new changes haven't broken existing functionality. Performed after every code change. Most commonly automated. Example: After adding a new payment method, re-test cart, existing payment, order history.

Q4. Explain Verification techniques: Walkthrough vs Inspection. Also explain Static vs Dynamic Verification. 8 Marks
WALKTHROUGH:
A semi-formal peer review where the author presents the document/code to 2-7 participants. Participants are NOT required to prepare in advance. The author introduces content and all participants ask questions freely. Goal: informal defect detection and knowledge sharing. Outcome: informal notes, no mandatory formal report.

INSPECTION:
The most formal and structured verification method. A team of 3-6 participants led by an impartial moderator. Everyone uses a checklist and follows formal rules. After the meeting, a formal report is prepared with defects and suggestions. Goal: maximum defect detection through systematic examination.

COMPARISON:

FormalitySemi-formalMost formal

STATIC VERIFICATION:
Checking software WITHOUT executing the code. Purpose: detect errors early in documents, design, or code. Activities: reviews, walkthroughs, inspections, static analysis tools. Question answered: "Are we building the product right?" Example: Reviewing SRS for contradictions.

DYNAMIC VERIFICATION:
Checking software BY EXECUTING the code. Purpose: ensure software works as expected during execution. Activities: unit testing, integration testing, system testing, UAT. Question answered: "Does the product actually work right?" Example: Running login module to check correct username/password works.
Q5. Explain Ad Hoc Testing and its types: Pair Testing, Exploratory Testing, Iterative Testing, Defect Seeding. 8 Marks
AD HOC TESTING:
Unstructured, informal testing performed without test plans or test cases. Performed by experienced testers based on intuition, domain knowledge, and creativity. Goal: quickly detect defects outside formal test conditions.

1. PAIR TESTING:
Two testers work together on the same machine — one operates (Driver) and one observes/reviews (Navigator). They switch roles periodically. Benefits: knowledge sharing, better coverage, fewer oversights. Example: One tester interacts with banking app while other documents observations.

2. EXPLORATORY TESTING:
Simultaneous learning, test design, and execution — all at the same time. Tester explores application without predefined scripts. Best suited when requirements are unclear or rapidly changing. Example: Tester begins testing a new feature with minimal knowledge, discovers defects, and simultaneously designs new test cases based on system behavior.

3. ITERATIVE TESTING:
Testing performed in cycles/iterations continuously alongside development. Each iteration builds on learnings from previous ones. Used in Agile/Scrum projects. Example: During sprint development, testers continuously test newly added features and update strategies based on feedback from earlier cycles.

4. DEFECT SEEDING:
Intentionally inserting known defects into the system to measure testing effectiveness. If seeded defects are found, it indicates real defects will also be found. Used in safety-critical industries.

Formula: Effectiveness = (Seeded Defects Found / Total Seeded) × 100

Numerical: 10 seeded, 6 found → Effectiveness = 60%. If 40 actual defects: 60% × 40 = 24 found.

Shortcomings: May introduce unintended bugs, increases complexity, distorts test metrics.
